Tecnologie Web · capitolo 5 · slide «API REST»

API REST

Come si progetta un'API web "come si deve": risorse con URI, operazioni con i metodi HTTP, rappresentazioni in JSON. Serve per lo scritto e soprattutto per il progetto. Negli scritti 2025 c'era da progettare gli endpoint di un servizio.

Prima di iniziare · cosa ti serve

URI (path e query) e i metodi HTTP con le loro proprietà. JSON è il formato dei dati: oggetti tra graffe con coppie "chiave": valore, liste tra quadre, es. {"nome": "Rossi", "tel": ["051 1", "051 2"]}.

§0 · Orientamento

Cosa chiedono all'esame

  • Progettare gli endpoint di un servizio (metodo + URI) partendo da una descrizione.
  • Distinguere collezioni (plurale, slash finale) e individui.
  • POST su una collezione contro PUT su un individuo per creare.
  • Perché REST è stateless e cosa ci guadagna (cache, scalabilità).
§1 · Concetti

API web e REST

Un'API web è un'interfaccia HTTP che permette ad altre applicazioni (automatiche, oppure web app con form e menu) di usare i servizi di un'applicazione.

REST · REpresentational State Transfer

È il modello architetturale del web "ben fatto". Le API non-REST inventano le loro funzioni e nascondono il protocollo di trasporto. Un'API REST usa direttamente HTTP (i metodi) e gli URI (i nomi) come interfaccia generica. L'obiettivo sono API consistenti, prevedibili e facili da usare.

§2 · Principi

Il modello CRUD e i quattro principi

CRUD: quasi tutte le operazioni sui dati sono Create, Read (di un individuo o di una lista filtrata), Update, Delete.

I quattro punti di REST

1. Ogni concetto rilevante è una risorsa. 2. Ogni risorsa ha un URI come identificatore. 3. Le operazioni si esprimono con i verbi HTTP (GET legge, PUT/POST creano o modificano, DELETE cancella). 4. Lo stato della risorsa viaggia come rappresentazione in un Content-Type preciso (JSON, XML…).

Il body di una richiesta o risposta non è la risorsa ma una sua rappresentazione.


PUT /clients/1234 HTTP/1.1
Host: www.sito.com
Content-Type: application/json; charset=utf-8

{ "nome": "Rossi S.p.A.", "tel": "051 654321", "citta": "Bologna" }
§3 · Naming

Individui, collezioni e URI gerarchici

Le regole sugli URI

Ci sono due tipi di risorsa: individui (un cliente) e collezioni (tutti i clienti), entrambi con un URI. Le collezioni sono plurali e si riconoscono dallo slash finale; gli individui sono singolari. Gli URI sono gerarchici, così rendono esplicite le relazioni.

/customers/ → collezione dei clienti
/customers/abc123 → il cliente abc123
/customers/abc123/ → le sotto-risorse del cliente
/customers/abc123/addresses/1 → il primo indirizzo del cliente

Filtri: quelli frequenti possono stare nella gerarchia (/regions/ER/customers/); gli altri vanno nella query della collezione: /customers/?tel=0511234567, /customers/?search=sales&value=100000&op=gt.

Altri consigli delle slide

Usa nomi coerenti; non copiare la struttura interna del database; prevedi parametri per filtrare e paginare; per le operazioni lunghe rispondi 202 Accepted con l'URL per controllarne lo stato. Per documentare un'API servono: gli endpoint (separando collezioni e individui), i metodi, esempi di input e output e i casi di errore.

§4 · Verbi

Verbi su collezioni e individui

La tabella delle slide

Elencare tutti i clienti → GET /customers/
Leggere il cliente abc123 → GET /customers/abc123
Creare un cliente, l'id lo decide il server → POST /customers/ (sulla collezione)
Creare un cliente, l'id lo decide il client → PUT /customers/abc123
Modificare tutti i dati di abc123 → PUT /customers/abc123
Aggiungere un telefono ad abc123 → POST /customers/abc123/telephones/
Cancellare abc123 → DELETE /customers/abc123

Semantica di POST: le vecchie specifiche dicevano "crea un subordinato della collezione". Dal 2014 (RFC 7231) POST vuol dire "elabora questa rappresentazione secondo la semantica della risorsa": è il verbo jolly, purché non si sovrapponga agli altri.

Verifica · §3–§4

4 domande

Vuoi creare un nuovo ordine e l'identificativo lo genera il server. Quale richiesta?

POST sulla collezione: il server crea l'individuo, sceglie l'id e risponde 201 Created con Location: /orders/<id>.

Quale URI rappresenta una collezione secondo le linee guida REST?

Plurale e slash finale: la collezione degli esami dello studente 42. /getExams è uno stile "a funzioni", non REST.

Come chiedi i clienti di Bologna con un filtro non previsto dalla gerarchia?

I filtri generici vanno nella query della collezione. Se fosse un filtro molto frequente si potrebbe esporre come /cities/bologna/customers/.

Perché REST si integra bene con le cache HTTP?

GET è sicuro e ogni risorsa ha il suo URI, quindi proxy e browser possono memorizzare le risposte. Con API "tutto POST" questo non è possibile.

§5 · Esercizio d'esame

Progettare gli endpoint di un servizio

Scritto 10/01/2025 · REST

Piattaforma di streaming musicale

Progetta metodo e URL per: (1) tutte le categorie musicali; (2) tutte le canzoni di una categoria, es. World Music; (3) il testo di una canzone specifica, es. "The Botanist" di C'mon Tigre.

Una soluzione possibile

  1. Si identificano le risorse: le categorie (collezione), le canzoni di una categoria (sotto-collezione), il testo di una canzone (sotto-risorsa dell'individuo).

  2. GET https://api.musica.it/categories/

  3. GET https://api.musica.it/categories/world-music/songs/

  4. GET https://api.musica.it/songs/the-botanist/lyrics (oppure /artists/cmon-tigre/songs/the-botanist/lyrics, se i titoli non sono unici)

  5. Tutte GET, perché sono letture (sicure e idempotenti). Nomi plurali per le collezioni, slash finale, identificatori leggibili. Nessun verbo nell'URI.

Errori tipici da evitare

Verbi negli URI (/getSongs, /deleteUser?id=3) · GET che modificano dati · tutte le operazioni in POST · collezioni al singolare · URI che espongono tabelle o file del server (/db/tbl_songs.php).
